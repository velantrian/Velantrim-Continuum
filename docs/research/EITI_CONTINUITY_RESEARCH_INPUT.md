# EITI Mechanisms as Continuity Research Input

Status: **RESEARCH / SHADOW ONLY · NO LIVE-WRITE AUTHORITY**  
Recorded: 2026-08-21

EITI already contains implementation evidence for local retrieval associations, salience/ranking, decay/accessibility, local learning analysis, context assembly and provider-switch continuity. Continuum may use these as empirical starting points for falsifiable continuity experiments; EITI behavior is not itself evidence that process continuity has been achieved.

```text
prototype behavior != continuity evidence
memory persistence != identity continuity
retrieval accessibility != epistemic status
provider switch success != process equivalence
pilot != proof
```

## Research hypotheses

### H1 — retrieval dynamics and recovery

Does preserving MOSC/PKG-like associative structure plus salience/accessibility state improve task recovery after model/runtime replacement compared with a simple static memory baseline?

Measure:
- recovery time;
- open-loop completion;
- relevant-context recall;
- contradiction rate;
- behavioral divergence;
- unnecessary-context load.

### H2 — decay without semantic corruption

Can DAAD-style decay reduce stale-context interference while preserving the ability to recover still-relevant evidence and commitments?

Hard invariant: decay changes accessibility, not truth, evidence existence, identity or authorization.

### H3 — provider/model replacement

EITI has E2E coverage for cross-provider context continuity. Continuum can use that as a prototype pattern, but must test stronger discontinuities: model family change, context loss, runtime restart and partial state transfer.

### H4 — adaptive learning vs continuity drift

Does proposal-first adaptation improve recovery without causing gradual goal/personality/process drift? Compare accepted/shadow proposals against frozen baselines and measure regression over longitudinal windows.

## Promotion criteria

A mechanism can leave research only after preregistered metrics, baselines, negative controls, repeated runs, failure taxonomy, provenance and explicit reassessment of write authority. Until then EITI is a useful implementation reference, not proof of continuity.
